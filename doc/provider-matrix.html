Packaging consequences

nghttp2 is the only provider that will not start without a third-party library. Everywhere else the native dependency is either supplied by the OS or needed only if you turn on HTTPS — so a plain HTTP build of any other provider ships as a single binary. An nghttp2 build always carries libnghttp2 ≥ 1.59 with it.

Only ICS bundles its OpenSSL. With ICS V9.7's default defines (OpenSSL_Resource_Files + OpenSSL_40 in OverbyteIcsDefs.inc) the OpenSSL 4 DLLs are embedded in the exe as resources and written to C:\ProgramData\ICS-OpenSSL\4000\ at first load, so there is no version hunt and no mismatch against a system-wide install. Measured 2026-10-08: the ICS TLS server reports OpenSSL 4.0.0 from C:\ProgramData\ICS-OpenSSL\4000\…, so the ICS TLS results in this matrix were obtained on OpenSSL 4, not 3.x. Every other TLS-capable provider expects you to supply OpenSSL and to keep its version in step.

Windows without OpenSSL is possible on two providers. HTTP.sys uses the Windows certificate store and SChannel in kernel space; IOCP has no TLS to configure. That removes OpenSSL from the deployment entirely — worth real money in environments where shipping crypto libraries triggers review.

mORMot is not one of them, despite the library supporting SChannel. The Horse provider exposes SSLCertFile + SSLPrivKeyFile as a PEM pair, and mORMot's SChannel server path wants something else entirely — mormot.net.sock.pas:1009 says the certificate on SChannel server, expects a .pfx / PKCS#12 binary content. So the provider's configuration surface only reaches the OpenSSL backend, and on Windows it additionally needs the FORCE_OPENSSL conditional: mORMot picks its TLS layer by whoever assigns NewNetTls first, and mormot.lib.openssl11 claims it unconditionally only under that define. Adding the unit to uses is not sufficient. This row previously read mORMot uses SChannel, which was inferred from the library rather than from this provider's config surface.

Version resolution is automatic where it exists. CrossSocket and nghttp2 probe for OpenSSL 3.x first and fall back to 1.1.x, trying each platform's naming convention in turn. ICS does not probe: the OpenSSL generation is fixed when ICS itself is compiled (see the ICS note above). Indy is the outlier: its classic IdSSLOpenSSL path is pinned to the OpenSSL 1.0.2-era libeay32/ssleay32 pair, which modern systems no longer ship.

epoll has no TLS at all — not a partial, an absence. Terminate TLS at a proxy in front of it.

mORMot alone has a build-time dependency. The mormot2static blob bundle must be extracted into mORMot2/static/ before anything compiles — precompiled .obj for Delphi, .o for FPC and Delphi Linux64. That is a build input, not a runtime file, and it is also what lets mORMot link OpenSSL statically for a genuinely self-contained binary — the only provider here that can.

Windows Services need the DLLs beside the .exe. The Service Control Manager does not inherit the interactive user's PATH, so a placement that works on a double-click fails when the service starts. Applies to every OpenSSL-using provider.

Do not mix OpenSSL families. 1.1.x and 3.x cannot coexist in one process, and code that dynamic-loads libssl-1_1 will not run on a host carrying only libcrypto-3. Pick one family per deployment.

Deployment

Two independent questions, and conflating them is the usual mistake. Binary shape is how the process is packaged and started. Fronting is what sits between the internet and that process — and there, in-process hosting and reverse proxying are not variations of one idea but opposites.

Read the n/a band carefully: it does not say Horse cannot run under IIS, Apache, CGI or FastCGI. It can, and those are well-supported targets. It says those modes replace the provider rather than run on top of one, so no provider column can answer for them.

The two hosting models

In-process — the web server owns the socket

  • Horse supports all four. Fully. ISAPI under IIS, an Apache module, CGI and FastCGI are first-class, long-standing Horse deployment targets. If you need one, use it — the framework, your routes and your middleware all work.
  • They are an alternative to a provider, not a feature of one These are the third axis of Horse's define model (HORSE_HOST_*), parallel to HORSE_PROVIDER_* rather than combinable with it. The host process accepts the connection and hands Horse a parsed request — there is no socket left for a transport provider to own.
  • Which is why those cells read "n/a", not "—" "Not available" would mean a gap. This is a category difference: asking which provider to use with ISAPI is like asking which engine to put in a towed trailer. Horse.pas makes it explicit with a {$MESSAGE FATAL} for every HORSE_PROVIDER_* × HORSE_HOST_* pairing, so the compiler names the conflict rather than letting you discover it at run time.
  • What you trade away The provider's capabilities go with it: no HTTP/2, no gRPC, no WebSocket, no event loop, no transport-level graceful drain. You inherit whatever the host process does instead — which for IIS and Apache is a great deal, just not these.

Reverse proxy — the provider keeps its socket

  • Works with every provider Horse self-hosts on a port; nginx, Apache or IIS forwards to it. This is the normal production shape, and it is how you get TLS termination, static-file serving and load balancing without giving up a provider's capabilities.
  • nghttp2 constrains what can front it It speaks HTTP/2 only, so the proxy must reach the backend over HTTP/2 — not merely accept HTTP/2 from browsers, which nearly all of them do. Most proxies downgrade to HTTP/1.1 on the back leg by default, and that back leg is what matters here.
  • Every other provider is HTTP/1.1 on the back leg Which is exactly what proxies do by default, so they are unconstrained.

Where the providers live

Internal — ship with Horse

  • IndyDelphi default for self-hosted builds. No define needed.
  • fphttpserverFPC default. No define needed.
  • HTTP.sysHORSE_PROVIDER_HTTPSYS — binds the Windows kernel HTTP stack via httpapi.dll.
  • epollHORSE_PROVIDER_EPOLL — Linux-native event loop.
  • IOCPHORSE_PROVIDER_IOCP — Windows completion ports over Winsock2.

External — installed via Boss

  • CrossSocketHORSE_PROVIDER_CROSSSOCKET — async HTTP/1.1, IOCP/epoll/kqueue.
  • mORMotHORSE_PROVIDER_MORMOT — the mORMot2 stack, incl. its own http.sys binding.
  • ICSHORSE_PROVIDER_ICS — OverbyteICS, modern OpenSSL. Delphi only.
  • nghttp2HORSE_PROVIDER_NGHTTP2 — libnghttp2. Requires Delphi-nghttp2 ≥ 1.7.0, which is where the gRPC layer itself lives; this provider is the adapter that mounts it on Horse.

What nghttp2 alone brings

Only here

  • gRPC as a transport Unary plus all three streaming shapes — server, client and bidirectional — with a protobuf codec, HTTP/2 trailers and two registration styles. Crucially it shares the port and connection with ordinary Horse routes: a /health endpoint and a gRPC service on one listener. The layer itself lives in Delphi-nghttp2, not here — it only ever took an INghttp2Stream, so nothing about it was Horse-specific. This provider contributes two guarded lines. That matters when comparing providers: what this row scores is a capability the transport library supplies, which the adapter exposes.
  • HTTP/2 you control HTTP.sys also serves HTTP/2, but the kernel negotiates it and hands you a finished request. nghttp2 exposes streams, trailers, GOAWAY and flow control — which is what makes gRPC possible on top of it.
  • HTTP/2 anywhere The only HTTP/2 option that is not Windows-only, and the only one that works on FPC.
  • Protocol-correct drain Two-stage GOAWAY per RFC 9113 §6.8: stop accepting new streams, let in-flight ones finish, then send a cutoff the peer can act on.

What you give up

  • HTTP/1.1 — entirely The server speaks HTTP/2 exclusively. HTTP/1.1-only clients cannot connect at all. This is the single biggest constraint and rules the provider out for public-facing endpoints without a terminating proxy.
  • WebSocket reaches fewer clients Implemented via RFC 8441 extended CONNECT and opt-in, but there is no RFC 6455-over-HTTP/1.1 path here. Browsers negotiate 8441 transparently; most non-browser WebSocket libraries cannot, and for them the result is "cannot connect" rather than a slower path. Indy, epoll and IOCP serve every client.
  • Zero-install simplicity Needs Delphi-nghttp2 ≥ 1.7.0 plus libnghttp2 ≥ 1.59 at runtime. Every internal provider needs nothing.
  • gRPC needs FPC trunk Only gRPC. The transport builds and passes on 3.2.2 like every other provider — this was listed here as "requires trunk 3.3.1, a hard blocker" until 2026-08-23, which overstated it by the whole transport. 3.2.2 lacks TCustomAttribute, so the attribute-driven codec cannot compile; define NGHTTP2_GRPC_NO_FFI and you get HTTP/2, TLS, streaming and WebSocket on the stock distro compiler.
  • Kernel-mode offload HTTP.sys parses and queues in kernel space with machine-wide port sharing. Nothing in userspace matches that on Windows.

Notes on the partials

TLS 1.3 + SNI — ICS is scored full because it ships OpenSSL 3.x/4.x and exposes SNI directly. CrossSocket, mORMot and nghttp2 reach TLS 1.3 only as far as the OpenSSL they find at runtime allows, and none exposes SNI as a first-class setting. HTTP.sys defers entirely to the Windows certificate store and netsh http add sslcert.

Cipher and version rows — OpenSSL configures TLS 1.2 cipher rules and TLS 1.3 cipher suites through separate calls, and SSLCipherList never affects TLS 1.3 — the connection most OpenSSL 3.x clients negotiate. ICS (v1.0.10), mORMot (v1.0.14), CrossSocket (v1.0.27) and nghttp2 (1.11.0) all restrict TLS 1.3 suites in a release today; the last two since 2026-10-07, on Horse 3.3.12, which carries the shared config fields (HashLoad/horse #597). ICS reads the list back, because OpenSSL silently drops a misspelled suite name next to a valid one; mORMot checks names against the five RFC 8446 suites instead (mORMot2 has no read-back) and needs mORMot2 2.4.16916+, refusing the field on older mORMot2 as v1.0.11 did. nghttp2 reads its list back like ICS; CrossSocket checks names against the RFC 8446 list like mORMot (DCS has no read-back). For the minimum version, ICS (v1.0.9), nghttp2 (1.11.0) and CrossSocket (v1.0.28, through DCS SetMinTlsVersion, winddriver #207) offer a real "TLS 1.3 only", all read back; Indy's SSLVersions can raise the floor but its stock OpenSSL path tops out at TLS 1.2, and mORMot fixes the minimum at TLS 1.2 with no setter. CrossSocket v1.0.27 refused htvTLS13 at Listen rather than ignore it; wire-checked in v1.0.28 by run-tls-tests C5a (a TLS 1.2 peer is refused) and C5b (TLS 1.3 served).

mTLS on HTTP.sys — configured outside the process, through the OS, not through Horse.

Every ● in the TLS and mTLS rows is now backed by a completed handshake, not by a config field. All three provider suites were run for the first time on 2026-09-24, and all three found something: the mORMot provider was serving plain TCP (FIX-MORMOT-TLS-1, v1.0.9); the CrossSocket gate had never executed, though its provider was correct; and the ICS provider accepted clients presenting no certificate at all while SSLVerifyPeer was set (FIX-ICS-MTLS-1, v1.0.6). That last one had no symptom — TLS completed, traffic flowed, a valid client certificate was honoured — so this row read ● on ICS and was wrong until that release. Re-verify these two rows by running each repo's run-tls-tests.bat, never by grepping for the config fields.

Event loop on ICS and nghttp2 — ICS uses its own message pump rather than a shared loop. nghttp2 defaults to thread-per-connection; the epoll/IOCP engine is opt-in via UseEventLoop.

Graceful shutdown — marked partial where the provider inherits the framework base rather than overriding StopListenGraceful with a transport-aware drain, so ATimeoutMS is accepted and discarded. What those providers do instead varies, and it is not uniformly "stop accepting without draining" — mORMot waits for in-flight work and then discards the reply. Read the measured paragraph below before inferring behaviour from a partial mark.

Graceful shutdown, measured rather than read (2026-09-24/25) — a drain probe per provider, 5 runs each, with a control: three distinct timings so elapsed time names the cause. A 5000 ms handler, the provider's own DrainTimeoutMs at 3000, StopListenGraceful(500), and shutdown fired 800 ms into the request. Control C0 — the same request undisturbed — passed 5/5 on every provider, which is what makes a lost response readable; without it a broken route and a severed request look identical. mORMot: FIXED 2026-09-27 (FIX-MORMOT-GRACEFUL-1), and upgraded to full — released 2026-09-28 in horse-provider-mormot v1.0.10. On the http.sys backend (mskHttpApi) the reply was lost on every run (11/11, WinHTTP 12030), because the drain counter drops before mORMot sends and THttpApiServer closes its request queue before joining its threads. v1.0.12 also waits for mORMot's own CurrentProcess = 0. Measured on v1.0.12: thread pool 60/60, async 60/60, http.sys 20/20. http.sys has further limits beyond shutdown (found 2026-10-06 by the integration suite, all in mORMot2's http.sys binding): chunked request bodies were delivered EMPTY — refused with 411 since v1.0.13 (FIX-MORMOT-HTTPSYS-CHUNKED-1, released); only the last Set-Cookie is sent; integration 118/126 vs 126/126 on the thread pool. It overrides StopListenGraceful as FServer.Shutdown → drain bounded by the caller's timeout → free, and returns in 735-752 ms for 700 ms of remaining work, with the reply intact in 79 of 80 runs. The one loss is unexplained and is NOT the async-write gap it resembles: a 60-run A/B with the settle at 0 versus 100 ms came back 60/60 both ways, so the default stays at 0 rather than gaining a delay on no evidence. Point estimate 1.25%; 60 runs rule out 5% but not 1%, and characterising it further needs ~184 runs per arm with no candidate mechanism to test — so it is recorded as a rare open defect with a detector (run-drain-batch.bat keeps each failing run's output) rather than chased. It earns the full mark because THttpServerGeneric.Shutdown only sets a flag and Request() then answers 404 to new work while in-flight requests keep their thread and socket — a clean refusal rather than a closed listener, which is exactly what lets it perform all three steps this row asks for. (The 404 is mORMot's choice; 503 would be better and would have to come from the pipeline.) It needs no settle delay, because it writes the reply synchronously in the request thread. Before the fix: 4200 ms (4199-4225) = 5000 − 800, bounded by neither timeout, reply lost every time (WinHTTP 12152) — and lost when the handler FINISHED, not when shutdown began, which is why its fix was a pure ordering change rather than CrossSocket's. ICS: FIXED 2026-09-27 (FIX-ICS-GRACEFUL-1), released 2026-09-28 in horse-provider-ics v1.0.8. It overrides StopListenGraceful and returns in 701-718 ms for 700 ms of remaining work with the reply intact, 5/5. Its drain is the best of the three because the correct wait is countable here: a finished ICS worker has only PostMessage'd its response, and the socket write happens on the main thread when the pump runs it, so the drain waits on FActiveRequests + FPendingMap + FPostBuffers under FPendingLock, on one shared deadline — no settle delay at all. Ending the pump early is what used to lose the reply: FServer.Terminated stops MessageLoop, and that loop is how ICS writes anything. Upgraded to full 2026-09-28 (FIX-ICS-GRACEFUL-2). It now stops accepting before draining, so it performs all three steps this row asks for. THttpServer.Stop is separably FWSocketServer.MultiClose (closes the listeners) then DisconnectAll (drops the clients), so MultiClose alone halts new connections while established clients keep their sockets — ICS's own idiom, used by SetPortValue to rebind a port under the comment "Do not disconnect already connected clients." Measured rather than assumed, because the equivalent step on CrossSocket destroys the in-flight body: 5/5 at 703-720 ms with the body asserted, and elapsed unchanged, so it costs nothing. Before the fix: 4204 ms (4196-4214), the same wait, but the response lost at ~810 ms — the instant shutdown began. So ICS blocked the caller as long as mORMot and gave the client less, and its 2026-08-22 upgrade to full is retracted here: downgraded to partial. CrossSocket: FIXED 2026-09-27 (FIX-CS-GRACEFUL-1), released 2026-09-28 in horse-provider-crosssocket v1.0.25. It overrides StopListenGraceful, honours the caller's timeout, and returns in 800-832 ms for 700 ms of remaining work with the response intact, 5/5 — against 4193-4203 ms and a lost reply before. Its mark stays partial, by this row's own criterion: it does not stop accepting during the drain. Closing the listening socket is what a graceful shutdown should do first, and in DCS it destroys the in-flight response body — headers go out, the body never does, and the client reads 200 with an empty body and no error at all. Proven by bisecting one step at a time; the mechanism is still unexplained. (An earlier 0/100/1000 ms settle sweep read as ruling out a flush race — that reading is RETRACTED: it was taken while CloseAllListens was still masking the race, and with the listener step gone a 0 ms settle fails about 1 in 2. The sweep was a measurement of the mask, not of the race.) Refusing new work belongs in the pipeline (IsShuttingDown → 503), not in the listener — which is effectively what mORMot does, and why it earns a full mark here while CrossSocket does not. The settle is GONE as of 2026-09-28 (FIX-CS-DEFER-1 + -2, provider commits ab8d6fd + a7893de), and that one WAS measured properly: the one-shot path now defers DecrementActive to CrossSocket's send-completion callback, as the streaming path always did, so the drain counter reaching zero means the bytes have left. A/B at HORSE_CS_SETTLE_MS=0, one machine: 4 failures in 60 runs before, 0 in 180 after, Fisher one-tailed p = 0.0036 — and every pre-change failure read Content-Length: 4 with body length 0, which is that window and not a severed connection, a timeout or a port collision (the probe reports each differently). DEFAULT_SETTLE_MS is now 0, worth ~100 ms off every graceful shutdown (10/10 at 696–714 ms against 808–819 with the sleep). So the earlier caveat that a response larger than the socket buffer could outlive the settle is retired — there is no window left to outlive. Horse.Provider.Console carries the identical sleep and was deliberately NOT touched: different write path, and generalising this result to it is the move that has cost time here. Before the fix it measured 4193-4203 ms (10/10 with its control across two builds, after its probe's earlier void runs turned out to be a port collision with a browser's DevTools endpoint, not a provider defect). Same wait as the other two — 4200 is 5000 − 800, the rest of the request, not the 3000 ms config value — and the in-flight response is lost at 809-819 ms — the instant shutdown begins, as on ICS. So all three external providers are now measured and all three behave the same way: the call is bounded by neither timeout, it waits out the whole request, and the client gets nothing. The differentiator this row used to claim does not exist anywhere in it.

Graceful shutdown, the earlier reading pass (2026-08-22) — kept for the reasoning it records, superseded above wherever the two disagree. It re-read each stop path rather than grepping for the method name, which had scored two cells wrong in each direction. Full marks require stopping accepts, then waiting on in-flight work, then tearing down. ICS was read as the only external provider doing all three in order: FServer.Stop, then FDrainEvent.WaitFor(DrainTimeoutMs) while an interlocked counter is non-zero, with the event signalled from a finally on both the success and exception paths — and upgraded to full on that basis. Running it disproved the upgrade: the ordering is real and buys nothing the client can see. HTTP.sys was downgraded: it closes the completion port and calls HttpCloseRequestQueue, which its own comment describes as cancelling pending calls, before joining its listener threads — that is a forced stop, not a drain. mORMot has the same machinery as ICS but frees the server first, and its comment concedes the counter "should already be 0" by the time the timeout is honoured — partial, and the measurement agrees. epoll joins each worker (Terminate; WaitFor), so in-flight handler work finishes, but there is no counter and ATimeoutMS is ignored — partial. IOCP and fphttpserver have no drain at all; they inherit a base that sets a flag, calls StopListen and discards the timeout.

Every mark in this row is for the static THorse facade. The Multi-Instance path (THorseInstance.StopListenGraceful) had two defects on top of it. Up to Horse 3.3.9 it called its own StopListen, discarding ATimeoutMS and bypassing every provider override — fixed in 3.3.10 by #590. That was not enough: Execute counts an instance-routed request on the instance's counter, while every built-in drain polled THorseCore's alone, so on the instance path the drain saw zero and closed the connection mid-request on IOCP, HTTP.sys, FPC.Daemon and FPC.LCL. Indy (Console/Daemon/VCL) survived because it also waits on its open contexts; CrossSocket, mORMot, ICS and nghttp2 count at the transport and were never affected. Proven 2026-10-03 by a control matrix (master fails on IOCP and HTTP.sys; fixing only the test's bind turns HTTP.sys's failure from “cannot connect” into “cut mid-request”; with the drain fix 12/12 pass) and filed as #599, merged and released in Horse 3.3.11 (2026-10-05; the six built-in drains plus Horse.Instance verified identical to our patch at the 3.3.11 tag). On Horse ≥ 3.3.11 the IOCP and HTTP.sys marks apply to THorseInstance too; on 3.3.10 and earlier, read them as applying to THorse only.

Do not confuse Horse's IOCP provider with nghttp2's IOCP engine. The column above is Horse.Provider.IOCP, which has no drain — that mark is unchanged. Nghttp2.Engine.Iocp is a different thing: the event-loop driver inside the nghttp2 provider, whose graceful shutdown was validated 2026-08-22 and delivered every in-flight response across all three shapes — 1 request, 4 concurrent on 4 connections, and 8 streams multiplexed on 1 connection — with the resolved driver asserted as IOCP completion port rather than a silent fallback. The nghttp2 column's full mark covers that engine, and now covers it on Windows as well as Linux.

WebSocket on fphttpserver — downgraded to partial: it depends on the application shape, not the transport. Horse.WebModule.pas registers an upgrader only inside {$IF NOT DEFINED(FPC)}, so the plain HTTPApplication shape has none and UpgradeToWebSocket takes the fail-fast path to 501. The Daemon and LCL shapes do register one (THorseWebSocketSocketUpgrader, via GetSocket), so WebSocket works there — subject to the FPC FeedBytes defect noted below.

WebSocket on nghttp2 — scored partial, and the caveat is reach rather than completeness. It is implemented via RFC 8441 extended CONNECT (:method CONNECT + :protocol websocket, answered 200 — HTTP/2 has no 101) and is opt-in via EnableWebSocket. Browsers negotiate it transparently; new WebSocket(...) is unchanged. Most non-browser WebSocket libraries speak RFC 6455 over HTTP/1.1 only, and this transport has no HTTP/1.1 to fall back to — so for those clients the result is "cannot connect", not "slower path". Validated end-to-end 2026-08-21 against a Python h2 client (build-fpc.sh stage 18, 4/4): extended CONNECT accepted, server frame delivered, and a masked client frame round-tripped. The partial mark reflects client reach, not completeness.

WebSocket receive was broken in shipped Horse on two paths — found while validating the above. Both are now merged and shipped: #551 on 2026-08-28, #549 on 2026-09-04, both in Horse 3.3.4. On 3.3.4 or later the ● marks in this row describe actual behaviour; on earlier releases they describe intended capability only. The maintainer reworked #549 rather than merging it as filed — errno is captured once and passed to both predicates, and close is deferred behind a state lock and an active-operation refcount instead of closing the descriptor under a blocked select(). Re-verified against that reworked code on 2026-09-05, 5/5 on FPC 3.2.2. (1) Horse.Provider.Socket.WebSocket.Read treats a non-blocking recv returning EAGAIN as a disconnect; epoll sets O_NONBLOCK on every accepted socket, so the read loop exits ~1 ms after the upgrade and nothing a client sends is ever delivered (PR #549). IOCP is unaffected — it leaves sockets blocking, verified. (2) On FPC only, Horse.Core.WebSocket.FeedBytes casts an interface reference back to a class, which FPC does not resolve, so OnMessage, OnBinary and OnError never fire (PR #551). Sending works in both cases, which is why they went unnoticed. The ● marks in this row describe intended capability; on epoll, and on FPC generally, receive needs those patches.

Streaming on fphttpserver — works through the default WebBroker stream writer rather than a transport-native one.

Keep-alive on fphttpserver was unusable before Horse 3.3.4. No row scores it, because every other transport here does HTTP/1.1 persistent connections natively and the comparison would be uniform — but this one is worth recording. KeepConnections defaults to False, and enabling it cost roughly 44 ms per request: fphttpserver writes each response as two send() calls and never set TCP_NODELAY on the accepted socket, so Nagle held the small second write until the peer ACKed the first, and the peer — with nothing to send — waited out its ~40 ms delayed-ACK timer. It was misread for a while as the keep-alive loop's select() poll interval; the server is idle in select() for ~43 ms, but waiting for a request the client cannot send because it is still waiting for a body Nagle is holding. Issue #562, fixed in #563: upstream sets TCP_NODELAY per connection via THorseNoDelaySocketHandler.Accept and sets a positive KeepConnectionTimeout, without which KeepConnections alone leaves the connection thread serving exactly one request. Measured after the fix: 30 requests on one reused connection, max 1 ms. Note this is a Horse-version property, not a transport capability — on Horse < 3.3.4 the same provider has it and it is slow.

Still open on Windows. 3.3.4 enables keep-alive on every platform but guards the TCP_NODELAY handler with {$IFDEF UNIX}, so FPC/Windows now has the stall's exact precondition — enabled keep-alive, no TCP_NODELAY — where before 3.3.4 it could not occur because keep-alive was off. Reported upstream; not measured here, as this workspace has no FPC/Windows setup.

gRPC here is server-side only. Every provider in this table is a server — that is what a provider is — so the row scores the ability to serve gRPC, and no column could answer otherwise. Worth saying because the ecosystem's other Pascal gRPC options split on exactly this: sgcWebSockets ships a client and no server, ultraware/DelphiGrpc does both. The client side lives in the library, not in any provider: since Delphi-nghttp2 1.28.0 (2026-10-14), Nghttp2.Grpc.Client's TGrpcChannel makes unary and server-streaming calls (deadlines, metadata, TLS + mTLS with server verification), and protogen --client generates typed stubs. It is tested against our own server, python grpcio and a raw HTTP/2 peer (library stage 4l, 71 checks; stage 4m, the generated stubs). Client and bidi streaming from the client are not there yet (GC5). It calls any gRPC server, so it is not scored per column here. See pascal-grpc-landscape.html for the client/server split across the wider ecosystem.

nghttp2 on FPC — partial because of the gRPC layer, not the transport. Full parity on trunk 3.3.1. On 3.2.2 the transport is fully supported — HTTP/2, TLS, mTLS, the epoll engine, streaming, backpressure and WebSocket RFC 8441 all build and pass there (25 stages, 0 failures, re-verified 2026-08-23). Only gRPC needs trunk, because 3.2.2's Rtti unit declares no TCustomAttribute, and it is separable behind NGHTTP2_GRPC_NO_FFI so the gRPC stages skip loudly rather than failing. Corrected 2026-08-23: this note previously read "unusable on 3.2.2", which was wrong and mattered — apt-get install fpc gives 3.2.2, and that is the compiler Horse's own CI installs. Separately, RegisterService<T> needs libffi even on trunk: it dispatches through TRttiMethod.Invoke, and FPC has no built-in call manager, so ffi.manager must be linked. The procedural RegisterMethod never reaches Invoke and needs none of it.

nghttp2 behind nginx — use grpc_pass, which speaks h2c to the backend, for both gRPC and plain HTTP/2 routes. A plain proxy_pass will not work: nginx's proxy_http_version tops out at 1.1, so the back leg cannot reach an HTTP/2-only server no matter what the front leg negotiates.

nghttp2 behind Apache — needs mod_proxy_http2 and an h2c:// backend URL. The commonly configured mod_proxy_http is HTTP/1.1-only on the back leg and will fail.

nghttp2 behind IIS — scored unavailable because ARR forwards to backends over HTTP/1.1 and offers no HTTP/2 back-leg option. Front an nghttp2 service with nginx or Apache, or expose it directly.

nghttp2 direct to internet — fine for gRPC, service-to-service traffic and controlled clients. Partial only because browsers reach HTTP/2 through TLS + ALPN, so a public endpoint needs a real certificate; and any HTTP/1.1-only client is refused outright rather than downgraded.

Shapes marked partial — the provider has no dedicated shape unit but still runs in that shape by driving Listen from the host's own loop or a worker thread. What you lose is the convenience base class (auto-Listen on form create, TService wiring), not the capability. epoll under VCL and IOCP/HTTP.sys under LCL are the notable cases.

ICS on Linux — not possible with ICS V9.x (corrected 2026-10-09; this cell was "◐"). ICS V9.7 refuses to compile for POSIX on purpose: OverbyteIcsTypes.pas line 177 holds the string 'ICS V9 does nbt build for Posix, use ICS V10' under {$IFDEF POSIX}, so the first real Delphi Linux64 build stopped with E2029. The provider's THorseICSLinuxDaemonApp was never compiled. Linux needs ICS V10 (beta), and the provider needs a port first: horse-provider-ics/plans/ics-v10-support.md. Grep: grep -an "use ICS V10" icsv97/Source/OverbyteIcsTypes.pas (-a: the file is not UTF-8)

A separate gRPC path exists. Horse ships Horse.Provider.Grpc, a standalone gRPC server with hand-rolled HTTP/2 framing. It is not a transport provider: it has no HORSE_PROVIDER_* define, runs its own listener on its own port, carries no TLS at all, and does not serve your Horse routes. Useful for h2c-only internal services; not a substitute for the nghttp2 row above.
